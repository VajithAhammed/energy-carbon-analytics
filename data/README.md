# Data Dictionary — Energy Consumption & Carbon Analytics

> ⚠️ **SYNTHETIC / SIMULATED DATA.** Every file in `raw/` is generated by
> [`src/generate_dataset.py`](../src/generate_dataset.py). It does not
> represent any real company, building, or utility. It is built to reproduce
> realistic *patterns* in building energy data (climate-driven load,
> occupancy-driven load, building-type baselines, aging-related
> inefficiency) — see [Why synthetic](#why-synthetic-data) below.

### `fact_energy` (91,350 base rows + 45 injected duplicates = **91,395 rows**)
Daily grain: 50 buildings × 1,827 days (2020-01-01 → 2024-12-31).
| column | type | notes |
|---|---|---|
| record_id | int | not a true PK after duplicate injection — see below |
| building_id | str | FK → dim_building |
| date | date | |
| electricity_kwh | float | **~1.2% null, 25 rows deliberately negative (data error)** |
| natural_gas_kwh | float | ~1.2% null |
| renewable_kwh | float | **subset of `electricity_kwh`**, not additional to it — the portion of total electricity use self-generated on-site (solar). Grid-purchased electricity = `electricity_kwh - renewable_kwh`. 0 for buildings without solar. This convention matters for carbon accounting (see `src/feature_engineering.py`). |
| peak_demand_kw | float | |
| occupancy_rate | float | 0–1 in valid rows; **20 rows deliberately >1 (data error)** |
| operating_hours | float | |

`carbon_emissions_kgCO2e` is **intentionally not a column here** — it's a
derived value (electricity × grid factor + gas × gas factor, minus
renewable offset), computed downstream via a join to `dim_emission_factor`
so the calculation logic lives in exactly one place.

### `fact_maintenance` (675 rows)
| column | type | notes |
|---|---|---|
| maintenance_id | int | PK |
| building_id | str | FK |
| maintenance_date | date | |
| equipment_type | str | HVAC / Electrical / Boiler / Lighting / Elevator |
| issue_type | str | Preventive / Corrective / Emergency |
| downtime_hours | float | |
| maintenance_cost | float | |

`issue_type = 'Emergency'` rows are disproportionately linked (a few days
later) to a genuine consumption anomaly — a realistic response-lag pattern,
useful later for explaining *why* an anomaly happened operationally.

### `data/processed/_validation_only_injected_anomalies.csv` (147 rows)
**Ground truth, held out from every modeling table on purpose.** Lists the
genuine equipment-failure-style spikes injected into `fact_energy`
(building_id, date, severity, likely cause). This is used **only** at the
end of the Anomaly Detection stage to sanity-check the Isolation Forest
model's recall — it is never joined into training data. If it were, the
"unsupervised" anomaly detection stage wouldn't be solving a real problem.

## Deliberately injected data-quality issues (for Stage 2)
| issue | table | count |
|---|---|---|
| Missing values (electricity_kwh, occupancy_rate, natural_gas_kwh) | fact_energy | 3,288 |
| Exact duplicate rows | fact_energy | 45 |
| Negative electricity_kwh (data error) | fact_energy | 25 |
| Occupancy_rate > 1 (data error) | fact_energy | 20 |
| Missing temperature | fact_weather | 73 |

These are **data errors** — distinct from the 147 **genuine anomalies**
above, which are valid (if unusual) readings that deserve investigation,
not deletion. Stage 2 builds the logic to tell them apart.

## Why synthetic data
Real public building-energy datasets (e.g. ASHRAE Great Energy Predictor
III, NYC Local Law 84 benchmarking) cover energy + weather at most. This
project's business case also needs occupancy, tariffs, emission factors,
renewables, and maintenance tied to the *same* building — no public source
joins all of that together truthfully. Stitching mismatched public
datasets would create fake joins; a controlled, clearly-labeled synthetic
dataset with real-world-shaped patterns and real-world-shaped mess is the
more honest choice. **This must stay labeled synthetic everywhere the
project is shown** — dashboard footer, README, resume, LinkedIn post.
